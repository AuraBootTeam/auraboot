# Generated CRUD default presentation

The standard model page workbench generates usable list, form and detail pages without a visual preset. Page generation does not require `presentation: workspace`, `formPresentation` or manual column styling. Business-specific groups, commands and child-table bindings remain explicit business configuration.

## Ownership and precedence

- Model/field metadata supplies types, dictionaries, reference targets, display identity and visibility/editability. Declared model `titleField`, or an existing field `displayField` declaration, identifies the detail record when it is bound and visible.
- The generator emits structural blocks and business bindings. The default list selects up to seven compact fields in binding order, prioritizing a declared display identity; explicit `listColumns` retain their selection and order. Saved views can add other authorized model fields.
- Generated forms carry localized create/edit titles. Generated details put their single edit action in the existing header toolbar, avoiding a second runtime footer.
- The declared object identity receives a readable default column width; explicit column widths and saved view widths still win.
- Destructive list actions default to the overflow menu. Existing saved pinning remains authoritative; enable/disable expressions are evaluated against the current selection, including all-matching selection.
- Shared renderers own page spacing, hierarchy and responsive presentation. Workspace-specific tabs, layout and actions remain compatible; default list headings receive the same visual hierarchy without selecting workspace behavior.
- Forms with up to four fields and no wide blocks default to a comfortable single column. Larger forms and child-table layouts use the existing wide layout. Explicit width/column properties and legacy workspace behavior take precedence.
- Long text, JSON, rich text and file controls receive full-width space in generated forms/details. Numeric, JSON and file types use their existing typed Smart components. Declared field component overrides remain authoritative.
- Explicitly visible, non-editable form fields are read-only and do not impose user-required validation. Runtime authorization remains mandatory; generated presentation never grants data access. Pure dynamic CRUD forms check the current create/update permission before mounting editable fields or child actions, including direct edit URLs. Explicit command, endpoint and embedded-host forms retain their own authorization contracts.
- Advanced form properties continue through `formPresentationProperties`, `PropertyFieldRenderer` and the registered editor extension seam. The generator wizard omits visual properties unless the author changes advanced settings.

## User journey

Open a model, select its pages workbench, generate CRUD, and open the generated runtime page. Automatic designer navigation is opt-in. Detail inspection requires selecting a real record; a detail schema is not an empty record preview. Existing generated pages are not silently regenerated by this change. Saving an unchanged dynamic CRUD edit returns a no-changes message without sending an empty mutation.

## Metadata freshness

Field version updates preserve omitted reference, feature, UI, rule and extension metadata and transfer dictionary bindings to the new version. Generated field guidance keeps i18n references and wraps source-language text in LocalizedText before schema validation.

Dictionary bind/unbind uses the same cache invalidation contract as field updates. Already-read model field metadata must reflect a changed dictionary on the next load; refreshing the browser must not require a backend restart.

## Verification boundary

The task implementation plan and acceptance ledger live in the Workspace documentation. Hermetic generator/property tests do not prove real-stack CRUD, child-table persistence, modal behavior or visual quality. Those require the same-runtime browser journey and reviewed original screenshots. No production rollout is implied.
